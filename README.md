# Visakh & Archana — invitation management

The existing React invitation now connects to a **FastAPI + SQLite** service. Hosts create personalized invitations at `/admin`; guests open `/invite/{random-token}` and send their RSVP directly to the database. Names and event access load at runtime, so creating or editing an invitation does not require a website rebuild.

## First-time setup (Windows PowerShell)

Run these commands from the project directory. Python 3.12+ and Node.js 22 are recommended.

```powershell
npm install
python -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -r backend/requirements-dev.txt
backend/.venv/Scripts/python -m backend.manage create-admin
```

The last command prompts privately for your admin username and password (12+ characters). There is no default account or password. Running it again resets the single account and signs out existing sessions.

For development, use two terminals:

```powershell
# Terminal 1 — API
backend/.venv/Scripts/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000 --reload --no-access-log
```

```powershell
# Terminal 2 — frontend (proxies /api to port 8000)
npm run dev
```

Open **http://127.0.0.1:5173/admin** and sign in. The root page is the generic invitation preview. Only generated invitation links deliver personalized responses to the backend; the root preview retains its explicitly labeled local draft mode.

On macOS/Linux, use `backend/.venv/bin/python` in place of `backend/.venv/Scripts/python`.

## One-server preview

Build React, then let FastAPI serve both the website and API:

```powershell
npm run build
$env:WEDDING_PUBLIC_ORIGIN = 'http://127.0.0.1:8000'
backend/.venv/Scripts/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000 --no-access-log
```

Visit **http://127.0.0.1:8000/admin**. Set `WEDDING_PUBLIC_ORIGIN` to the address guests actually use: it controls the links generated by the dashboard. A local address works only on your computer; public sharing needs deployment to a reachable server.

## What hosts can manage

- Create invitations for a person or family, with **Wedding only** or **Wedding + reception** access. There is no guest allowance or configured maximum per invitation.
- View/copy a unique link, edit the name/events without changing the link, and deactivate/reactivate it.
- Search and filter a paginated guest list; see pending, accepted and declined responses and attendance totals per celebration.
- Inspect names, contact details, guest counts, selected celebrations, transportation, accommodation, dietary requirements and messages.
- See responses flagged for review after event access changes. Incompatible event responses remain visible to the host, are excluded from attendance totals, and are not exposed to the guest's restricted invitation.

A wedding-only link removes reception venues, program, dress guidance, transport, RSVP options and calendar entries. The API independently rejects reception participation from these invitations. Guests can reopen their link to edit an existing response. A response's guest count applies to each event the respondent selects; separate headcounts per event are not collected in this version.

## Data and authentication

The default database is `backend/data/wedding.sqlite3`. SQLite foreign keys, WAL mode, transactions and numbered schema migrations keep persistence isolated from presentation. No database or credentials are committed. Guest responses are persisted server-side; personalized drafts stay in memory rather than browser localStorage.

Admin access uses a hashed password, expiring HTTP-only session cookie, CSRF checks, origin checks and sign-in throttling. There is one admin account. Guest links use long random tokens: possession of a link allows viewing/updating that invitation's response, so forwarding a link grants the same access. Deactivate a link to stop access.

Saves use idempotency keys. Retrying a request does not create duplicate invitations or replace a newer RSVP with an older retry. Admin edits include a version check so a stale edit cannot silently replace changes from another browser. API errors and expired sessions preserve editable values where possible.

## Deployment settings

| Environment variable | Purpose / default |
|---|---|
| `WEDDING_DATABASE` | Persistent SQLite file; defaults to `backend/data/wedding.sqlite3` |
| `WEDDING_PUBLIC_ORIGIN` | Exact website origin, no trailing path; development default `http://127.0.0.1:5173` |
| `WEDDING_COOKIE_SECURE` | Set `true` when served over HTTPS; local development default `false` |
| `WEDDING_ALLOWED_ORIGINS` | Additional permitted origins, comma separated. Set to an empty string in production when only the public origin is needed. |

For a public server, build `dist/`, install `backend/requirements.txt`, use a durable local disk/volume for SQLite, set the public HTTPS origin and secure cookies, and run Uvicorn behind an HTTPS reverse proxy. Use one application worker for this small service. Do not host the database on an ephemeral or network filesystem. Configure proxy logs to redact `/invite/{token}` and `/api/invitations/{token}` paths; tokens grant guest access. The documented `--no-access-log` avoids recording them in Uvicorn logs. Private routes send no-store, no-index and no-referrer headers. Frontend-only static hosting cannot run this backend.

Keep secret credentials out of `VITE_` variables, which are public browser build inputs. Deployment is not performed by this implementation.

## Backups and recovery

Create a consistent backup using SQLite's backup API, including committed WAL data:

```powershell
backend/.venv/Scripts/python -m backend.manage backup backend/data/backups/wedding-backup.sqlite3
```

Use a new filename each time; existing backups are not overwritten. Copy backups to protected storage on another device. To restore, stop the service and point `WEDDING_DATABASE` at a restored backup in a new directory, then restart. This avoids mixing restored database files with stale WAL files. Test restoration before relying on a backup schedule.

## Verification

```powershell
npm test
npm run build
backend/.venv/Scripts/python -m pytest backend/tests -q
npm run test:management
```

The management browser check creates its own temporary database, test admin and server. It never uses the live database. It requires a built `dist/` and Playwright Chromium (`npx playwright install chromium`). The existing invitation smoke check remains available with Vite running on port 5173:

```powershell
npm run test:browser
```

Screenshots and test artifacts are stored in ignored `qa/`.

## Structure and future memories

- `backend/`: API, validation, authentication, SQLite migrations, admin/backup CLI and tests.
- `src/Entry.tsx`: admin, generic and personalized route entry points.
- `src/App.tsx`: guest invitation, event-dependent details and calendar download.
- `src/components/AdminPage.tsx`: protected management dashboard.
- `src/components/RsvpPage.tsx`: guest RSVP form, validation and recovery.
- `src/data/wedding.ts`: shared wedding content and program.
- `DESIGN.md` and `UX-CONTRACT.md`: visual and interaction conventions.

The wedding is on **11 February 2027**; ceremony **11:00–11:20 AM**, reception **6:00–10:00 PM**, in **Asia/Kolkata**. Calendar files use UTC instants.

The database migration structure and separate API modules leave room for albums, photos and stories later. That future phase should store image files in file/object storage and album metadata in the database. No galleries or upload service are included yet.
